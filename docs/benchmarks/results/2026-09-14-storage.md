## What the benchmark changed

The first run measured **202 ms** for a three-hop traversal at 10⁵ edges —
about twenty times the design's expectation, at ten times fewer edges.

The cause was in the implementation, not the benchmark. Traversal was a single
recursive CTE with a `LIMIT` on the outer query. A recursive CTE expands the
**entire** reachable set before any outer `LIMIT` applies, so the node cap
bounded the *output* and not the *work*. On a Zipf-distributed call graph, a
reverse three-hop walk from a hot symbol therefore materialised most of the
graph on every call — and impact analysis runs before every edit.

Moving `LIMIT` inside the CTE did not help: measured against this driver, it
truncated the result without terminating the recursion.

Traversal now expands level by level, with the node cap checked between hops
and a row cap per level. Each level is a bounded indexed lookup against
`edges_forward` / `edges_reverse`.

Measured head to head in `evals/graph/`, which keeps the recursive-CTE
strategy as a baseline so the comparison stays reproducible:

| Strategy | 3-hop, 10⁵ edges | 3-hop, 10⁶ edges |
|---|---|---|
| Recursive CTE (previous) | 221 ms | not measured |
| Level-wise (current) | **28 ms** | **26 ms** |

`TestStrategiesAgree` asserts both strategies return the same node set at the
same depths, so the speedup is not from doing less work.

The second row is the important one: cost is now bounded by the node cap rather
than by graph size, which is the property an interactive budget needs.

[DR-2](../../adr/0002-graph-in-sqlite.md) is unaffected — the graph is still
SQLite edge tables, and its stated disadvantage ("deep or analytical graph
queries are slower") is exactly what showed up here.

## Reproducing the comparison

```console
$ go test -run TestStrategiesAgree ./evals/graph     # they agree
$ go test -run '^$' -bench . -benchmem ./evals/graph # they differ in cost
```

## Open questions

- **`VectorScan` at 42 ms exceeds the 10–30 ms estimate.** Semantic retrieval
  is optional and off by default, so this is not blocking, but it is the number
  that would decide whether `sqlite-vec` is needed if it is ever enabled. A
  SIMD-friendly layout or a flat `[]float32` arena would likely close the gap
  before an index is warranted.
- These ran on tmpfs. The write-path numbers on a real volume are unknown.
- Single run, not `-count 6` with `benchstat`. Variance is unmeasured.

$ make bench
