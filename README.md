**A supervised coding engineer that runs entirely on your machine.** A
deterministic harness wraps a local model: the repository is indexed into a
typed code graph, every action is journalled before it happens, verification
runs in a sandbox, and nothing reaches your working tree until a human has
approved a diff.

The model is the least trusted component in it — see
[trust boundaries](docs/explanation/trust-boundaries.md).

[Limitations](#honest-limitations) · [Documentation](docs/index.md) ·
[Roadmap](ROADMAP.md)

> **Status: pre-1.0, under active development.** The task pipeline works end to
> end — retrieval, a bounded tool loop editing a confined worktree, verification
> inside a Landlock sandbox, a completion contract decided from evidence, and a
> human gate carrying the diff. What is **not** done is a task set large enough
> to evaluate against, so this README claims no success rate. Language coverage
> is uneven rather than absent: Go is deepest, TypeScript needs the sidecar for
> a call graph. See [ROADMAP.md](ROADMAP.md).

## What it does

Most local coding assistants lose to two problems: a small context window, and a
model that cannot hold a large codebase in its head. This attacks both from
outside the model.

**Questions about the repository are answered before the model sees anything.**
A typed code graph, a lexical index and an execution journal live in SQLite. The
supervisor answers structural questions from those and hands the model only the
slices the current step needs, so the context window stops being the binding
constraint.

**Every project is isolated by construction.** A workspace is the unit of
isolation, identified by a hash pinned in the repository. Its index, ledger,
telemetry, cache, artifacts and engine directories are separate files in
separate directories, and the storage API cannot be called without a workspace
handle. There is no global memory and no cross-project channel.

**Work survives interruption.** Every model-visible action journals its intent
*before* the side effect and its outcome *after*. A crash leaves uncertainty,
and recovery resolves it by inspecting the worktree rather than assuming success
or failure.

**A model's claim of success decides nothing.** A task is accepted only when
every check its level requires has a passing result *against the current state
of the code*. A skip, an error, or a pass against an older state satisfies
nothing. Then a human gate carries the diff and the findings, so approving means
reading what the supervisor computed rather than trusting a summary.

**Verdicts come from a table, not an opinion.** Compatibility is decided
deterministically from the change kind and the edge kind. A missing edge means
"not discovered", never "does not exist", and the report says so every time.

## Install

Docker is the only host dependency. For GPU inference you also need the NVIDIA
driver and the NVIDIA Container Toolkit.

```bash
docker volume create le-data
docker run --rm -v le-data:/data alpine chown -R 10001:10001 /data

docker run -d --name local-engineer \
  --gpus all \
  -v le-data:/data \
  -v "$HOME/code":/work \
  -p 127.0.0.1:7777:7777 \
  ghcr.io/akynte/local-engineer:latest
```

Omit `--gpus all` on a CPU-only host. Keep the `127.0.0.1` prefix — the
supervisor can run sandboxed commands and read every indexed repository, so it
must not be reachable from your network.

Then point it at a repository:

```bash
docker exec -it local-engineer le doctor          # what is actually in effect
docker exec -it local-engineer bash -c 'cd /work/my-project && le workspace init && le index'
docker exec -it local-engineer bash -c 'cd /work/my-project && le graph impact MyFunc --change signature'
docker exec -it local-engineer bash -c 'cd /work/my-project && le task verify'
docker exec -it local-engineer bash -c 'cd /work/my-project && le plan "add retries to the payment client"'
```

`docker compose -f deploy/docker-compose.yml up -d` wraps the same thing, and
`deploy/docker-compose.split.yml` is the conventional multi-container layout.
To run without Docker, see
[install on the host](docs/how-to/install-on-the-host.md) — and what isolation
layer that costs you.

**From source**, for contributors: `make build` produces `./bin/le`, and
`make check` runs CI's format, vet, lint, test, isolation, schema and task-set
gates locally. Go and Docker are the prerequisites;
[CONTRIBUTING.md](CONTRIBUTING.md) has the detail.

## Honest limitations

The full list is [known limitations](docs/explanation/known-limitations.md), and
`le doctor` reports the runtime ones at startup. These are the ones most likely
to change your mind about using this:

- **The published task-success numbers settle nothing.** A real run exists — 3
  tasks × 4 arms × 5 passes, 60 runs against a local model on disclosed hardware
  — but every arm's confidence interval overlaps every other's, and 4 of the 12
  task/arm cells changed verdict between passes. The code graph's contribution
  remains *measurable* rather than *measured*. What the run does show is that
  false acceptance is real and quantifiable: the unsupervised baseline claimed
  success on work that failed the hidden test in 4 of 15 runs. Storage and graph
  latency numbers **are** published. See
  [the results](docs/benchmarks/results/).
- **Process-level isolation between concurrent tasks needs bubblewrap**, which
  is usually unavailable inside a container, so it is off by default. Isolation
  from your host and between workspaces does not depend on it.
- **A task never reaches the network.** Verification runs with `GOPROXY=off`,
  and no flag grants a task egress. A change needing a new dependency is an
  operator's `le deps sync` through a separate confined lane, on a port no task
  is granted. That lane is off by default.
- **TypeScript has no call graph without the sidecar.** The `cpu` and `cuda`
  images carry it; the `-slim` image does not. Without it the analyzer still
  indexes imports, declarations, heritage clauses and `process.env` reads, and
  every edge records which reading produced it — so the two are told apart
  rather than blurred.
- **SQLite needs a real filesystem with working `fsync`.** Not an overlay layer,
  not a network share. `le doctor` fails if you use one.
- **The shipped hardware profiles are starting points, not measurements.** Run
  `le models bench --write` on your own machine; `le doctor` warns until you do.
